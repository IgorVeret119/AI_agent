# Эксперимент A/B: выбор инструментов и петли

Данные: 100 инструментов (4 настоящих `schedule_*`, 96 синтетических отвлекающих, из них 28 близких по смыслу), 30 размеченных запросов, 20 задач для агента. Описания настоящих инструментов извлечены из существующего `server.py`; основное расписание и его сервер не изменяются.

Модель выбора и агента: **Qwen/Qwen3-0.6B**, официальный GGUF **Q8_0**. Модель поиска: **Qwen/Qwen3-Embedding-0.6B**, официальный GGUF Q8_0, last pooling. Размер обеих моделей — около 0.6B. Это результаты квантованной версии, а не утверждение об идентичности результатам BF16. Скачивание требует интернет; inference и эксперименты выполняются локально на CPU. API-ключи не нужны. SHA256, revision и версия llama.cpp записываются в `results/model-manifest.json`.

## Повторить

Используйте окружение Python проекта, где установлен MCP 2.2.0; дополнительно нужен `requests==2.34.2` (он уже есть в основном requirements-lock).

```powershell
python experiments/download_models.py --directory D:/lesson-02-mcp-demo/.runtime/qwen-experiments
python experiments/run_all.py --runtime D:/lesson-02-mcp-demo/.runtime/qwen-experiments --output experiments/results-new
python -m pytest experiments/test_experiments.py -q -p no:cacheprovider
```

`run_all.py` запускает две модели на 127.0.0.1:18080 и 18081, выполняет A, B и анализ, затем останавливает собственные процессы. На Windows окна скрыты. Занятые порты дают явную ошибку. Если серверы уже запущены, можно выполнить отдельно:

```powershell
python experiments/run_selection.py
python experiments/run_loops.py
python experiments/analyze.py
```

`data/*.json` зафиксированы до эксперимента. Не перестраивайте данные после просмотра ошибок модели: `build_data.py` предназначен для осознанного создания новой версии датасета. Вложенные пулы и хэши файлов находятся в `data/dataset-manifest.json`. Идентификаторы запросов и золотые метки проверяются тестами.

## Часть A

Четыре настоящих инструмента есть в каждом пуле N=5,20,50,100. Пулы вложенные, отвлекающие смешаны по фиксированному seed. A передаёт все N описаний. B строит индекс исключительно по описаниям (без имён, золотых меток и вопросов), использует cosine similarity, извлекает top-5 в текущем пуле. Для query embedding используется рекомендованная Qwen форма `Instruct: ...\nQuery: ...`. Поиск детерминирован при сохранённых эмбеддингах; Recall@5 имеет знаменатель 30, а не 90.

Модель возвращает JSON `{"tool":"..."}`. Схема ограничивает структуру, но не подсказывает верный инструмент и не ограничивает имя enum: имя вне каталога считается ошибкой. Исполнение инструментов для A не требуется. Общее правило «наиболее специфичный применимый инструмент» одинаково для A/B и устраняет неоднозначность между поиском и специализированным `schedule_day`/`schedule_room`. Золотые метки не видны модели.

На каждом запросе выполняются 3 независимых генерации с разными seed; итого **720** ответов: 30 × 3 × 4 × 2. Порядок описаний перемешивается для каждого повтора; A и B сохраняют одинаковый относительный порядок. При N=5 обе стратегии получают тот же каталог — полезный контроль. Блоки N/вариант/повтор и порядок запросов перемешиваются фиксированными seed. KV-кэш разрешён, но токены учитываются из полного `usage.prompt_tokens`.

Точность считается по всем 90 генерациям клетки, ошибки JSON и неверные имена не исключаются. 95%-й percentile bootstrap: 10 000 выборок 30 **запросов**, у каждого сохраняются три повтора. Дополнительно рассчитана парная разница B−A тем же способом. Семантический поиск, LLM-токены и входные токены query embedding показаны раздельно; разовый индекс не скрыт в среднем.

## Часть B

`unstable_server.py` — отдельный MCP-сервер с экспериментальной версией `schedule_search`, фильтром `date`, исходной синтетической фикстурой и тремя условиями. Он использует MCP 2026-07-28 через настоящий stdio-клиент; `_meta` есть в каждом запросе.

С вероятностью 0.5 каждый вызов получает инъецированный пустой ответ. Bernoulli-испытание определяется явным `fault_handle=seed:ordinal`. При одинаковой задаче/повторе/номере вызова маска совпадает во всех условиях. Сервер не хранит RNG, номер эпизода или сессию. Операционные `fault_handle` и `response_mode` добавляются harness, а не моделью, и исключены из определения одинакового **доменного** вызова.

- `baseline`: пустой результат `[]` без объяснения, без guard.
- `guard`: тот же инструмент; guard проверяет предложение до исполнения и останавливает эпизод перед третьим одинаковым вызовом или перед завершением A-B-A-B. Окно — 6.
- `hint`: вместо пустого ответа сообщение «Ничего не найдено; попробуйте другое значение date в разрешённом интервале», без guard.

**Материал лекции не был предоставлен.** Здесь реализован guard по двум критериям из задания; соответствие конкретному алгоритму лекции не заявляется. Если лекция требует другой политики (например, подсказку вместо остановки), замените `core.LoopGuard` и способ обработки `guard_stop` и выполните новый прогон.

Каждый вариант: **20 задач × 3 повтора = 60 эпизодов**; всего 180. Задача — найти хотя бы одно занятие нужного курса в закрытом 8-дневном интервале, начиная с указанной даты. Альтернативные даты допускаются задачей, поэтому подсказка не заставляет нарушить запрос пользователя. Неизменяемое расписание развёрнуто в даты как повторяющийся недельный шаблон.

Максимум 12 шагов. Шаг — вызов модели, в том числе финальный ответ и заблокированное предложение. Средние токены — сумма входных/выходных usage по всем шагам, включая повторно переданную историю. Успех проверяется программно: финальные entry_id/date должны соответствовать реально полученной записи нужного курса внутри интервала. Само получение записи без корректного финального ответа ещё не успех.

Петля: ≥3 одинаковых исполненных вызова подряд либо A-B-A-B с разными A и B. Дополнительно показана доля эпизодов с попыткой такого паттерна, блокированной guard: нулевая доля исполненных петель сама по себе не доказывает, что модель научилась планировать. Для B также рассчитаны CI и парные разницы по 20 задачам, сохраняя повторы. Прерывание по лимиту не считается петлёй без фактического паттерна.

## Артефакты

- `results/REPORT.md`: итоговые таблицы, интервалы и ответ, что помогло сильнее.
- `results/summary.json`: численные метрики и парные интервалы.
- `results/selection.jsonl`: 720 реальных ответов, полные prompts, usage и метки.
- `results/retrieval.json`: top-5 и hit на 120 сочетаниях запрос/N.
- `results/embeddings.json`: настоящие нормированные эмбеддинги и расход токенов.
- `results/loops.jsonl`: 180 эпизодов со всеми действиями, результатами MCP и причинами остановки.
- `results/loop-mcp-wire.json`: JSON-RPC обмен нестабильного сервера.
- `results/model-manifest.json`: provenance и SHA256 весов и движка.
- `results/audit.json`: независимый пересчёт правильности, успеха и петель по сырым ответам, проверка seeds/масок и сумм токенов.
- `results/run-settings.json`: параметры сэмплирования, лимиты, политика guard и хэши исходников/данных.

После сбоя JSONL-файлы позволяют продолжить, пропуская завершённые наблюдения. Используйте новый output-каталог для другой модели, параметров, данных или guard. Анализ требует полного набора 720/180 наблюдений и не строит итоговый отчёт по частичному прогону. Ошибки HTTP не превращаются в неверные ответы модели: прогон останавливается и может быть продолжен.
