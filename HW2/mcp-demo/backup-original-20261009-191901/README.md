# Дополнение: настоящий MCP через stdio

Основной семинар разбирает контракт инструмента на стандартной библиотеке. Здесь тот же тип задачи проходит через официальный MCP SDK: клиент запускает отдельный локальный процесс сервера, получает каталог, вызывает инструменты и читает ресурс. LLM не используется. Расписание — вымышленная учебная запись.

Из этой папки:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python client.py
```

На Windows используйте `.venv\Scripts\python.exe`. Зависимости загружаются при установке; сам пример не обращается к внешним сервисам и не открывает сетевой порт. Сервер закрывается вместе с контекстом клиента. В stdout сервера нельзя писать произвольные отладочные строки: этот канал занят протоколом.

Проверьте вывод: две функции в каталоге, сумма 12, аудитория 314, отклонение неверного типа и неизвестного инструмента. Для аргументов сложения используется `StrictInt`: строка `"7"` тоже отклоняется, как в строгом контракте основного семинара. Версия протокола читается из реального соединения. Число 314 не является сведением о занятиях курса.

Три вопроса к коду:

1. Какая часть выполняется в процессе клиента, а какая — в процессе сервера?
2. Почему корректное соединение и найденный инструмент ещё не означают, что модель выбрала правильное действие?
3. Что изменится, если вместо stdio использовать удалённый HTTP-сервер? Где понадобятся аутентификация, таймауты и проверка доверия?

SDK зафиксирован на версии 2.2.0; эта программа использует API ветки v2. [Официальный SDK](https://github.com/modelcontextprotocol/python-sdk), [клиент](https://py.sdk.modelcontextprotocol.io/client/), [транспорт stdio](https://py.sdk.modelcontextprotocol.io/client/transports/).

Пример использует локальный транспорт stdio. В нём нет native tool calling модели, OAuth и удалённого сервера; отдельный процесс сервера не обеспечивает его изоляцию от системы.
